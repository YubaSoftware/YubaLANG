# YubaLANG 1.4.0 release notes

> **Status:** 1.4 is still in progress. This page documents the features
> delivered so far. The full planned scope is in the
> [1.4 roadmap](../roadmap/1.4.md) and the working checklist in
> [todo.md](../../todo.md).

YubaLANG 1.4.0 keeps the 1.3 command style and adds expression function calls,
attribute/index/method access, lambdas, optional chaining, collection iteration,
destructuring, enums and `match`/`case`, type aliases, constants, compound
assignment, and unpacking. It also adds record field defaults with named
construction, deterministic resource cleanup, typed errors, configurable
runtime limits, a broad standard-library expansion, an interactive debugger
frontend, opt-in test coverage, and a cached language server workspace index.
The release remains interpreter-only.

## What is new in 1.4.0

### Function calls in expressions

Expressions can call user-defined and imported standard-library functions with
positional or named arguments. Calls may be nested and may appear wherever an
expression is accepted:

```hl
func define double value:int -> int
    return value * 2
endfunc

define var total: int = double(3) + double(value=4)
text output total
```

`range(...)` and the empty `set()` constructor keep their existing expression
forms. Calls share the 128-frame limit and runtime diagnostics of `func call`.
Expressions may also use attribute, index, slice, and method access with chained
receivers.

### Language ergonomics

Expressions support attribute access, indexing, slicing, and methods. Lambdas
are values of function types and callbacks for `map`, `filter`, and `sorted`.
`?.`, `?.[...]`, `?.(...)`, and `?:` provide optional chaining and
null-coalescing. `*` and `**` unpack sequences and mappings in calls and
collection literals:

```hl
define var names: list[string] = ["Ada", "Grace"]
define var double: (int) -> int = lambda value: value * 2
define var maybe: string | none = none
text output names[0].upper()
text output map(double, [1, 2, 3])
text output maybe ?: "fallback"
```

`loop for <target> in <iterable>` iterates collections, strings, and other
iterables. Targets may destructure tuples and lists. Declarations and
assignments also support tuple/list destructuring, with arity and type
diagnostics.

### Enums and matching

Enums group named variants, optionally with typed payloads. `match`/`case`
supports literal, tuple, type, binding, wildcard, and enum patterns plus an
optional `else`. Enum matches that omit variants and have no `else` produce
`non-exhaustive-match` in both the checker and the runtime; malformed patterns
produce `invalid-pattern`:

```hl
enum define Result ok(value: int) error(message: string)
enum create Result.ok success 42
match success
    case Result.ok(value)
        text output value
    case Result.error(message)
        text output message
endmatch
```

Type aliases name existing types and work in annotations, records, and function
signatures. `define const` declares immutable variables, a `const` marker makes
record fields immutable, and compound assignments (`+=` through `>>=`) keep the
same declared-type rules as `set`.

### Record defaults and named construction

Record fields may declare a default value, and `record create` accepts named
field values after any positional values:

```hl
record define Settings retries:int=3 label:string="default"
record create Settings settings label="strict"
record create Settings positional 5
```

Defaults are evaluated for each construction, so mutable defaults are not
shared. Missing required fields, unknown names, duplicates, positional values
after named values, and type mismatches are reported. A field type may name a
record defined later in the same source file; the referenced record must exist
before an enclosing value is constructed. Record methods, inheritance, and
code-running constructors remain deferred.

### Deterministic resource lifecycle

The runtime tracks resources with a `close()` method. Files opened with `open`
are registered automatically, and all tracked resources close in reverse
registration order when execution ends. Cleanup attempts every resource even
when an earlier close fails, then raises the first error. Hosts can call
`Runtime.register_resource`, `close_resource`, and `close_resources`; repeated
registration and repeated close are safe.

### Runtime and standard library

The bundled standard library adds `std.regex`, `std.glob`, `std.tempfile`,
`std.archive`, `std.sqlite`, `std.uuid`, `std.decimal`, `std.statistics`,
`std.logging`, `std.terminal`, `std.env`, `std.io`, and `std.sys`. Regex and
glob support compiled patterns, replacement, and sorted path expansion.
Temporary files and native handles participate in deterministic cleanup.
ZIP archives reject traversal and symlink entries during extraction. SQLite
supports parameter binding, explicit transactions, bounded result sets, and
idempotent handle closure. Decimal arithmetic avoids binary floating-point
rounding surprises, and statistics accepts finite numeric lists.

File I/O gains sized reads, `readline`/`readlines`, `writelines`, `seek`,
`tell`, `flush`, `truncate`, line iteration through `iter`, binary standard
streams through `std.io`, and atomic replacement through `std.fs`.
`std.fs.atomic_write_text`, `atomic_write_bytes`, and `replace` expose
crash-safe replacement without partial writes.

Errors caught by `try`/`catch` are now dictionaries with `kind`, `message`,
`code`, `cause`, `stack`, and `value`. The string form remains the message, so
existing programs that print a catch variable continue to work. New
`catch <kind> as <variable>` blocks filter by kind, and
`error <kind> <message> <destination> [cause]` constructs an error value
without throwing it. Stack frames are plain data and never expose a Python
traceback.

Recursion depth, collection size, HTTP timeouts and response sizes, and
subprocess timeouts and output sizes are configurable through the host
`Runtime` and through `std.sys.set_limit`. Defaults are documented in the
standard-library reference. Dictionaries keep insertion order, sorted
standard-library results are stable, and sets do not promise iteration order.

### Interactive debugger

`YubaLANG debug [--break [file:]line]... <file.yl>` drives the existing debugger
hooks from a terminal. It supports breakpoints, continue, step, next, finish,
stack, variables, source listing, and quit. Prompts and diagnostics go to
standard error so program output is unchanged. Hosts can also embed
`lang.debugger_frontend.DebuggerFrontend` with custom input and output
functions.

### Test coverage

`YubaLANG test --coverage` collects executable-line hit counts through the
`YUBALANG_COVERAGE_FILE` side channel and reports overall and per-file
percentages plus uncovered lines. JSON output gains an additive `coverage`
object. Coverage is opt-in, so the default output comparison and report shape
are unchanged. Blank lines, comments, and block terminators are not executable.

### Language server workspace index

The server indexes `.yl` files under initialized workspace folders on demand,
caches them by modification time, and invalidates entries on open, change,
close, and watched-file notifications. Workspace symbols, completion, unique
definition lookup, references, and rename can include unopened files.
Workspace-wide rename and references apply only to top-level variables,
functions, and record types; locals and parameters remain limited to open
documents, and ambiguous matches are not changed. Hidden and dependency
directories and files larger than 1 MiB are skipped.

### Static analysis and package metadata

The static checker resolves forward record types, understands record defaults
and named construction, accepts union values that the runtime accepts, checks
optional boolean conditions, and infers expression-call result types. It also
narrows optionals and unions across `if`, `elseif`, `else`, and early-return
branches, and infers comprehension filters, collection `get` and `getattr`
results, and simple alias chains. Match exhaustiveness, match-block scoping, and
constant reassignment are also checked. YubaLANG 1.4 accepts project manifests
targeting runtime 1.2, 1.3, or 1.4 and creates new projects targeting 1.4.
Registry resolution and installation remain YubaPKG responsibilities.

### Diagnostic codes and check modes

Every parser, checker, and runtime diagnostic now carries a stable code and a
severity. Human-readable output appends the code in brackets, LSP diagnostics
expose it in the `code` field with severity `1` for errors and `2` for warnings,
and `YubaLANG explain <code>` prints a short description with an example:

```text
YubaLANG explain type-mismatch
```

`YubaLANG check` reports both errors and warnings and fails only on errors.
`--deny-warnings` fails when a warning is reported, and `--strict` enables
strict-only checks (currently `invalid-annotation`) and also fails on warnings.
Neither flag changes execution behavior. `check --json` emits a versioned
`schemaVersion: 1` object with stable `code`, `severity`, `message`, and
one-based range fields plus an error and warning summary. See the
[diagnostic reference](../features/diagnostics.md).

## Migration guidance from 1.3

The release is additive for documented 1.3 programs:

- Existing `func call` statements remain valid and are still appropriate for
  calls whose result is discarded.
- Positional record construction is unchanged. Named and default fields are
  optional additions.
- New expression, loop, destructuring, enum, match, alias, lambda, constant,
  compound-assignment, optional-chaining, and unpacking forms are additive; no
  documented 1.3 program changes meaning.
- Existing files close as before, now through the general resource protocol.
- The test runner output is unchanged unless `--coverage` is passed.
- Manifests targeting `1.3` remain accepted; new projects target `1.4`.

See the [1.3 to 1.4 migration notes](1.4-migration.md) and the
[1.4 language reference](../1.4-docs.md).

## Deferred work

Concurrency and asynchronous I/O remain deferred until cancellation, error
propagation, scheduling, and shared-state rules are specified. User-defined
generics, record methods, generators/`yield`, and language-level cleanup/defer
forms remain deferred pending proposals. Record methods require a separate
receiver, mutation, visibility, equality, and compatibility proposal. Build or
bundle commands need concrete generated-code and native dependency use cases
plus reproducibility and platform requirements. Bytecode targets, class-based
inheritance, and broader native FFI remain gated on measurable need and safety
proposals. Registry resolution stays in YubaPKG.

## Compatibility notes

- YubaLANG 1.4 continues to accept `1.2` and `1.3` project manifests.
- New projects created by 1.4 target `yubalang: "1.4"`.
- The package importer reads lockfile formats 1, 2, and 3. YubaPKG remains the
  tool that resolves registry dependencies and writes format 3.
- The language server, formatter, debugger, and test runner are covered by the
  repository test suite; the stdio LSP also has a standalone smoke test.
