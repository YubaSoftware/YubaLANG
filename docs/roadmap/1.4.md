# YubaLANG 1.4 roadmap

Status: **in progress.** YubaLANG 1.4 closes the everyday gaps in the command
language, expands the bundled standard library, and brings the editor, debugger,
test runner, formatter, and REPL to a consistent level of completeness. The
release stays interpreter-only; concurrency, bytecode execution, broader FFI,
and application bundling move to 1.5 or later.

The working checklist is [todo.md](../../todo.md). It is the canonical item list;
this page records motivation, sequencing, dependencies, and release gates. Keep
YubaLANG runtime responsibilities separate from YubaPKG package resolution and
installation.

## Release intent

1.3 and the delivered part of 1.4 established the core model: grouped commands,
typed variables, functions and closures, records, modules, resources, and a
stdio language server. The remaining friction is mostly ergonomic:

- Common operations still need commands (`getattr`, `list get`, `func call`)
  where an expression would read naturally.
- Loops iterate over counts rather than collections, so nearly every traversal
  needs an index variable or an iterator command pair.
- Records have defaults and named construction but no methods, enums, or sum
  types, so dispatch is written with string tags and conditionals.
- Diagnostics have messages but no stable codes, severities, or machine-readable
  output.
- Tooling is present but uneven: no LSP formatting or semantic tokens, a minimal
  formatter, a golden-output-only test runner, and a debugger without watches or
  conditional breakpoints.

1.4 addresses those gaps without changing the execution model. Existing 1.3
programs must keep working, and each syntax addition ships with parser,
checker, runtime, formatter, LSP, and reference updates in the same change.

## Delivered baseline

These items are already in the repository and remain covered by regression
tests:

- [x] Expression function calls with positional and named arguments.
- [x] Record field defaults, named construction, and forward record field types.
- [x] Static analysis for the delivered record, union, optional, and expression
  call cases.
- [x] Deterministic resource protocol with reverse-order cleanup and automatic
  file tracking.
- [x] `YubaLANG debug` frontend over the existing hooks.
- [x] Opt-in `YubaLANG test --coverage`.
- [x] Cached LSP workspace index with safe top-level references and rename.
- [x] Editor setup documentation and automated LSP protocol tests.
- [x] Manifest compatibility for runtime 1.2, 1.3, and 1.4.

The 1.4 release notes currently describe this delivered subset. They are
finalized again at the end of Milestone 6.

## Milestone 1 - Language ergonomics

Make expressions expressive enough for ordinary data manipulation, then extend
the type model.

**Work areas**

- Attribute, index, and method access in expressions, including chains.
- `loop for <name> in <iterable>` with destructuring and the existing
  `break`/`continue` rules.
- `match`/`case` over literals, tuples, types, and enum variants, with
  exhaustiveness checking.
- Enums and sum types with payloads.
- Type aliases and user-defined generics for functions and records.
- Lambdas, `define const`, immutable fields, compound assignment, optional
  chaining, null-coalescing, and unpacking.
- Record methods and code-running constructors after an accepted proposal.
- Generators/`yield` and lazy iterators integrated with resource cleanup.

**Sequencing**

1. Expression access and `for` loops first: they are the highest-frequency
   ergonomic wins and unblock cleaner examples.
2. `match` and enums together, because exhaustive matching depends on enum and
   union representations.
3. Type aliases and generics before methods, so method signatures can use them.
4. Lambdas and unpacking after call syntax is settled.
5. Record methods and generators last: both need design proposals and affect
   scope, cleanup, and compatibility.

**Exit criteria**

- Every addition has a grammar entry, checker rule, runtime check, formatter
  behavior, LSP completion/hover entry, and reference section.
- Existing command forms remain valid; no 1.3 program changes meaning.
- Invalid receivers, arity, patterns, and exhaustiveness produce coded,
  source-located diagnostics.
- The 1.4 reference documents which forms remain unsupported.

## Milestone 2 - Types and diagnostics

Turn static analysis from a best-effort extra into a dependable, documented
layer while keeping runtime checks authoritative.

**Status:** Delivered for the syntax that exists in 1.4. Optional and union
narrowing covers `if`, `elseif`, `else`, and early-return branches. Inference
covers comprehension filters, collection/index/`getattr` results, and simple
alias chains. Stable codes, severities, check modes, JSON output, `explain`, the
inference audit, and negative fixtures are complete. Narrowing for `match` and
inference for patterns, lambdas, and methods are wired to the shared fact
helpers but cannot run until the milestone 1 syntax lands; their diagnostic
codes are registered and documented.

**Work areas**

- Narrowing for optionals and unions across `if`, `elseif`, and early-return
  branches; `match` narrowing follows the milestone 1 syntax.
- Inference for comprehension filters, collection/index/`getattr` results, and
  simple alias chains; pattern, lambda, and method inference follow their
  milestone 1 syntax.
- Stable diagnostic codes, severities, `--strict`/`--deny-warnings`,
  `check --json`, and `explain`.
- A documented audit of inference limits and the dynamic cases that remain
  unchecked.

**Exit criteria**

- Codes are stable and covered by negative fixtures.
- `--strict` never changes default execution behavior.
- `check --json` has a versioned, documented schema.
- The reference states exactly what the checker can and cannot prove.

## Milestone 3 - Runtime and standard library

Fill the gaps that force projects to shell out or vendor helper code.

**Work areas**

- Text and data: `std.regex`, `std.glob`, `std.archive`, `std.sqlite`.
- Runtime utilities: `std.tempfile`, `std.uuid`, `std.decimal`,
  `std.statistics`, `std.logging`, `std.terminal`, `std.env`.
- File I/O: `seek`, `tell`, `readline`, line iteration, buffering, binary
  standard streams, and atomic replacement.
- Error values that can be caught by kind and inspected as data.
- Configurable limits and deterministic ordering/hashing guarantees.
- Resource protocol coverage for iterators and native handles.

**Exit criteria**

- Every module has API reference, examples, failure-mode documentation, and
  platform notes.
- New file and archive APIs cannot silently overwrite data or escape a target
  directory.
- SQLite, archive, and temporary resources participate in normal cleanup.
- Limits have documented defaults and tests that exercise them.

## Milestone 4 - Documentation and developer experience

Bring the surrounding tools to the same level as the language.

**Documentation and REPL**

- Doc comments and `YubaLANG doc` output for files, directories, and projects.
- A diagnostic reference and a syntax/built-in cheat sheet.
- REPL history, completion, `:type`, `:doc`, and `:load`/`:save`.

**Formatter**

- Configuration for indentation, line width, and comments.
- Doc-comment formatting and stable comment attachment.
- Idempotence and fuzz coverage over the example catalog.

**Language server**

- Formatting, semantic tokens, folding, highlights, and inlay hints.
- Call hierarchy and completion snippets.
- Doc-comment hover and signature documentation.
- Code actions and refactors: add import, extract variable/function, implement
  record.
- Multi-root workspaces and record-field rename.

**Debugger**

- Conditional breakpoints, watches, expression evaluation, and exception
  breakpoints.
- A machine-readable event stream and attach support for tests and the REPL.

**Test runner**

- An in-language `test`/`expect` format alongside golden-output tests.
- Name filtering, parallel jobs, timeouts, and setup/teardown hooks.
- JUnit XML and TAP output, coverage thresholds, and branch coverage.

**Command line**

- `YubaLANG init`, `YubaLANG version --json`, and color/`NO_COLOR` support.

**Exit criteria**

- The default test-runner output and JSON shape stay unchanged unless a new
  option is passed.
- LSP features are covered by stdio protocol tests and a recorded manual editor
  smoke test.
- Formatter output is stable across repeated runs.
- Every tool command is documented in the master reference and its focused
  guide.

## Milestone 5 - Projects and distribution

Keep package resolution in YubaPKG while making manifests express what a project
actually requires.

**Work areas**

- A manifest `features` list.
- Version-range validation such as `>=1.4 <2.0`.
- Offline `package verify`.
- Project API documentation generation.
- Compatibility-matrix and package-test updates.
- Lockfile changes only after coordination with YubaPKG.

**Exit criteria**

- Mismatched runtime capabilities produce actionable errors before execution.
- YubaPKG remains the only tool that resolves and installs registry packages.
- The compatibility matrix is tested in both directions where possible.

## Milestone 6 - Quality and release

**Work areas**

- Conformance suite for every grammar rule, built-in, type rule, and diagnostic.
- Negative fixtures, fuzz tests, and runnable examples for all new behavior.
- CI on Windows, Linux, and macOS across supported Python versions.
- Benchmark regression thresholds.
- Manual desktop-editor verification.
- Final release notes, migration guide, and documentation index.

**Exit criteria**

- All suite, conformance, documentation, formatter, LSP, and smoke tests pass on
  every supported platform.
- No new feature is documented only in a roadmap; the versioned reference and
  master reference match the shipped behavior.
- Migration notes cover every compatibility-sensitive change.

## Dependencies and risks

- **Record methods, generators, and pattern matching** can grow without bound.
  Each needs an accepted proposal with explicit non-goals before implementation.
- **LSP and formatter work** can double the surface area of every syntax change.
  Treat tooling updates as part of the feature, not follow-up work.
- **Diagnostic codes** become a compatibility surface once published; assign
  them before the release and avoid renaming afterward.
- **Standard-library modules** carry platform and security obligations. Modules
  without a clear failure model are deferred rather than shipped half-specified.
- **CI cost** rises with the platform matrix; benchmark thresholds must be
  stable enough to avoid false failures.

## Deferred from 1.4

- Concurrency and asynchronous I/O are planned for 1.5 with cancellation,
  error propagation, scheduling, and shared-state rules.
- Interpreter performance, profiling, and a bytecode/VM path are planned for 1.5
  behind measured gates.
- FFI v2 with pointers, strings, structs, callbacks, and ownership is planned
  for 1.5.
- Application build/bundle commands move to 1.6.
- Non-C extension mechanisms and class-based inheritance remain unscheduled.
- Registry resolution and installation remain YubaPKG responsibilities.

## Completion criteria

A 1.4 change is complete only when its behavior is specified, tested,
documented in the versioned and master references, covered by migration
guidance when compatibility is affected, and validated on the platforms
required by its scope.
