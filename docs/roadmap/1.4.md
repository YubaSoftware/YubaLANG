# YubaLANG 1.4 roadmap

YubaLANG 1.4 ships the accepted language, runtime, and tooling candidates and
records the candidates that remain deferred. YubaLANG runtime responsibilities
stay separate from YubaPKG package resolution and installation.

## Shipped in 1.4

### Language and data model

- [x] Add expression function calls for simple and qualified names, positional
  and named arguments, and nested calls. Keep attribute/index receivers,
  argument unpacking, and calls on call results unsupported.
- [x] Add record default field values and named construction after positional
  values. Evaluate defaults per construction and diagnose missing, unknown,
  duplicate, misordered, and mistyped fields.
- [x] Allow a record field type to name a record defined later in the same
  source file, while requiring the referenced record to exist before an
  enclosing value is constructed.
- [x] Improve static analysis for forward record types, record defaults and
  named construction, union values, optional boolean conditions, expression-call
  result types, and multi-token annotations. Keep runtime checks authoritative
  and document inference limits.

### Runtime and resource lifecycle

- [x] Define and implement a deterministic resource protocol:
  `Runtime.register_resource`, `close_resource`, and `close_resources`, with
  reverse-order cleanup, every-resource attempts, first-error reporting, and
  automatic file tracking.
- [x] Decide concurrency and asynchronous I/O remain out of scope until
  cancellation, error propagation, scheduling, and shared mutable state are
  specified and testable. The API remains synchronous.

### Developer experience

- [x] Add the `YubaLANG debug` frontend over the existing debugger hooks:
  breakpoints, continue, step, next, finish, stack, variables, source listing,
  and quit, with prompts on standard error.
- [x] Add opt-in `YubaLANG test --coverage` using a side-channel collector so
  default exact-output behavior is unchanged. Report executable-line counts,
  per-file percentages, uncovered lines, and additive JSON coverage.
- [x] Add an on-demand LSP workspace index with mtime caching and invalidation
  by open, change, close, and watched-file notifications. Restrict
  workspace-wide rename/references to top-level symbols and keep locals within
  open documents.
- [x] Document editor setup and add a workspace-index protocol test.
- [ ] Complete a manual smoke test in a desktop editor session. The server
  protocol and workspace behavior are covered by automated stdio tests, but CI
  does not launch a GUI editor.

### Projects and distribution

- [x] Keep registry resolution and installation in YubaPKG.
- [x] Accept manifests targeting runtime 1.2, 1.3, or 1.4 and create new
  projects targeting 1.4. Update the compatibility matrix and package tests.
- [x] Record the build/bundle requirements before designing a command: concrete
  generated-code and native dependency use cases, reproducible inputs,
  platform targets, artifact layout, and interaction with YubaPKG.
- [x] Update the versioned reference, master reference, migration notes, release
  notes, examples documentation, installation guide, and tool guides.

## Explicitly deferred

- Record methods, inheritance, and constructors that execute code need a
  separate proposal covering receiver semantics, mutation, visibility,
  equality, and compatibility.
- Concurrency and asynchronous I/O need cancellation, error propagation,
  scheduling, and shared mutable state rules; no async API ships in 1.4.
- A build/bundle command needs representative generated-code and native
  dependency projects before its reproducibility and platform requirements can
  be designed.
- Bytecode or compiler targets are not a 1.4 goal: current benchmarks do not
  demonstrate a measurable need.
- Class-based object orientation, a non-C plugin system, and broader native FFI
  types remain gated on concrete use cases, ABI and ownership rules, platform
  support, and process-safety limitations.
- Registry resolution and installation remain in YubaPKG.

## Completion criteria

A 1.4 change is complete only when its behavior is specified, tested,
documented in the versioned and master references, covered by migration
guidance when compatibility is affected, and validated on the platforms
required by its scope.

See the [long-term YubaLANG feature backlog](features.md) for candidates that
may fall outside 1.4.
