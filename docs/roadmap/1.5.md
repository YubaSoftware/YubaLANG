# YubaLANG 1.5 roadmap

Status: **planned.** YubaLANG 1.5 is the performance and concurrency release.
It makes the interpreter substantially faster, adds bytecode execution behind
measured gates, introduces a deterministic asynchronous runtime, and widens
native interoperability. It does not attempt application bundling; that work
moves to 1.6.

The 1.5 baseline is the completed 1.4 release. The 1.4 work is tracked in the
[1.4 roadmap](1.4.md) and [todo.md](../../todo.md).

## Release intent

1.4 makes the language comfortable to write. 1.5 makes it fast enough for
larger workloads and capable of doing several things at once without giving up
deterministic behavior. The release has four anchors:

1. **Interpreter speed.** Reduce startup and execution cost before adding a new
   execution engine.
2. **Bytecode where it pays.** Add a compiled path only when benchmarks show a
   repeatable win over the optimized tree-walker.
3. **Deterministic async.** Add tasks, cancellation, and channels with a
   single-threaded default scheduler and a testable virtual clock.
4. **FFI v2.** Turn the narrow value-only C bridge into a usable systems
   boundary without making memory safety invisible.

Everything in 1.5 must preserve 1.4 program behavior unless a migration guide
and a major-version exception explicitly say otherwise.

## Milestone 0 - Baseline and gates

Before implementation, capture a reproducible 1.4 baseline and turn it into CI
gates.

- [ ] Extend `tools/benchmark.py` to report startup, parse/check time, function
  calls, loops, arithmetic, collections, records, string building, and module
  loading separately.
- [ ] Add representative multi-file project and HTTP/process/file workloads.
- [ ] Record memory use and allocation counts for the same workloads.
- [ ] Publish the baseline in `docs/tools/performance.md` with the exact machine
  and command used.
- [ ] Add CI thresholds with enough headroom to avoid flaky failures.

**Provisional targets**

| Area | Target versus 1.4 |
| --- | --- |
| Startup | at least 40% faster |
| Function calls | at least 2x throughput |
| Loop and arithmetic workloads | at least 2x throughput |
| Collection construction and iteration | at least 1.5x throughput |
| Memory | no regression above 10% on the tracked workloads |

Targets are finalized after the baseline is recorded. A target that cannot be
met without a semantic compromise is renegotiated before release, not silently
dropped.

**Exit criteria**

- The benchmark harness runs on all supported platforms.
- Results are comparable across runs and stable enough for CI.
- Every later milestone reports against this baseline.

## Milestone 1 - Interpreter speed

Optimize the existing tree-walking interpreter and front end. This milestone is
independent of bytecode work and must land first.

**Work areas**

- Avoid re-tokenizing and re-parsing expression sources; cache normalized
  expression trees with source locations.
- Replace linear command-dispatch chains with table or dictionary dispatch and
  remove repeated prefix comparisons.
- Reduce per-call allocations: frames, argument dictionaries, scope objects,
  and temporary tuples.
- Speed up scope lookup with interned names and precomputed local slots while
  preserving closures and dynamic globals.
- Add fast paths for the common typed cases in assignment, comparison,
  arithmetic, and collection mutation, keeping the general path authoritative.
- Reduce import and module-loading overhead, including repeated manifest and
  lockfile reads.
- Improve startup by deferring optional tool imports and avoiding work that only
  the REPL, LSP, or test runner needs.
- Profile the standard-library wrappers and remove avoidable conversions.

**Exit criteria**

- Provisional speed targets are met or explicitly renegotiated with data.
- No behavioral change in the full suite, conformance suite, or examples.
- Error locations and call frames are unchanged.
- A short profiling guide explains how to find the next bottleneck.

## Milestone 2 - Bytecode and caching

Add an execution path that is faster than the optimized interpreter on real
workloads, and keep the interpreter available as the reference implementation.

**Work areas**

- Lower the validated command and expression tree to a compact instruction
  format with source maps.
- Implement a stack or register VM covering variables, scopes, calls, closures,
  records, collections, exceptions, and resources.
- Keep runtime checks authoritative; the VM must produce the same diagnostics
  and cleanup order.
- Define cache artifacts: bytecode versioning, source hash, runtime version,
  invalidation rules, and safe fallback.
- Add a user-facing switch while the VM is experimental, then make it the
  default only after it wins on the release gates.
- Measure compile time against execution time so short scripts do not regress
  from compilation overhead.
- Document the distribution and trust model for cached artifacts.

**Sequencing**

1. Instruction format and source maps.
2. Straight-line commands, arithmetic, and control flow.
3. Functions, closures, and records.
4. Exceptions, resources, and cleanup order.
5. Cache and invalidation.
6. Default switch after gates pass.

**Exit criteria**

- The VM matches interpreter output on the full suite and conformance corpus.
- The VM is faster than the optimized interpreter on the tracked workloads and
  not slower on startup-sensitive scripts.
- Corrupt, stale, or mismatched caches are ignored safely.
- A documented switch returns to the interpreter for debugging.

## Milestone 3 - Profiling and observability

- [ ] Add `YubaLANG profile <file.yl>` with per-command and per-function timing.
- [ ] Add allocation and collection-size summaries.
- [ ] Add optional tracing for calls, imports, resource cleanup, and task
  scheduling.
- [ ] Keep profiling output out of normal program stdout.
- [ ] Publish worked examples for finding and fixing a slow program.

**Exit criteria**

- Profiling adds no overhead when disabled.
- Reports identify the hottest command and function without requiring Python
  knowledge.
- Documentation explains how to interpret the report.

## Milestone 4 - Concurrency and asynchronous I/O

Add structured concurrency with deterministic scheduling by default.

**Language surface**

- `async func` declarations and `await` expressions.
- `spawn`/task creation and structured task scopes or task groups.
- Cancellation tokens with cooperative checks at await points and loop
  boundaries.
- Channels with bounded and unbounded modes, plus `select` over channel and
  cancellation events.
- Timeouts and deadlines as first-class values.
- Error propagation: fail-fast groups, aggregated errors, and cancellation
  cleanup that cannot leak resources.

**Semantics**

- The default scheduler is single-threaded and deterministic for a fixed
  program.
- Shared mutable collections and records follow explicit rules: captures are
  reference-based like today, and the reference documents why that is safe or
  unsafe under scheduling.
- Await points are cancellation points; blocking standard-library calls must be
  wrapped rather than faked.
- Resource cleanup runs when a task completes, fails, or is cancelled.
- Task failures never terminate the process silently.

**Standard library**

- Async variants for filesystem, process, HTTP, and socket operations.
- Streaming HTTP bodies with backpressure.
- Timers and a virtual clock for deterministic tests.
- Optional TCP/HTTP server helpers, only if their lifecycle and limits are
  specified.

**Testing**

- Scheduler tests use the virtual clock and a fixed task order.
- Cancellation tests cover cleanup, nested groups, and partially completed work.
- Error-aggregation tests cover multiple simultaneous failures.

**Exit criteria**

- Every async API has a deterministic test path.
- Cancellation cannot skip resource cleanup.
- The reference states the ordering and fairness guarantees precisely.
- Blocking calls inside async code are diagnosed.

## Milestone 5 - FFI v2

Widen the C boundary while keeping ownership explicit.

**Work areas**

- Additional scalar types, pointers, `cstring`/UTF-8 strings, fixed arrays,
  structs by value and by pointer, and out-parameters.
- Callbacks with documented lifetime and thread restrictions.
- Ownership and borrowing annotations for pointers, with no hidden copies.
- Error-code to exception mapping and a documented calling-convention check.
- Build-time ABI validation where platform information is available.
- A safe wrapper pattern for common library shapes, without generating bindings
  automatically in 1.5.
- Evaluate a non-C extension path (for example WASM or a subprocess protocol)
  and record a recommendation; implementation is deferred.

**Exit criteria**

- Unsupported signatures fail with actionable diagnostics rather than crashes
  where detection is possible.
- The guide documents memory ownership, platform differences, and crash risk.
- Tests cover strings, structs, callbacks, out-parameters, and error mapping on
  every supported platform.
- Async interaction rules are stated and tested for callbacks.

## Milestone 6 - Tooling and release gates

- [ ] Add a Debug Adapter Protocol front end over the debugger.
- [ ] Extend LSP with large-workspace performance tests, test-explorer
  integration, and async-diagnostics ordering.
- [ ] Add function coverage and HTML coverage reports, building on the branch
  coverage delivered in 1.4.
- [ ] Keep formatter behavior stable under the new syntax.
- [ ] Update the language server, formatter, debugger, test runner, and
  migration guides for 1.5.

**Release gates**

- 1.4 suite, conformance suite, examples, and documentation tests pass on
  Windows, Linux, and macOS across supported Python versions.
- Performance targets are met and published against the recorded baseline.
- Async, FFI v2, and bytecode each have a compatibility and migration section.
- The bytecode path can be disabled; the interpreter path remains supported.
- No 1.4 program changes behavior without documentation and migration guidance.

## Explicitly not in 1.5

- **Application build/bundle commands.** Moved to 1.6. 1.5 produces faster
  execution and cache artifacts, not distributable application bundles.
- **Registry resolution and installation.** Remain YubaPKG responsibilities.
- **Non-C plugin mechanisms.** Evaluated in 1.5, implemented later only with a
  concrete integration need.
- **Class-based inheritance.** Requires a separate object-model proposal.
- **A JIT.** Bytecode is the only compilation target considered in 1.5.
- **Distributed or multi-process runtimes.** Out of scope until single-process
  concurrency is stable.

## Dependencies and risks

- **Benchmark noise** can invalidate the release gates. Baseline hardware,
  warm-up rules, and tolerance must be fixed before optimization starts.
- **Bytecode scope** can expand into a second implementation of the language.
  The interpreter remains the reference, and the VM must reuse the same
  front-end and runtime services.
- **Async semantics** are easy to specify and hard to test. The virtual clock and
  fixed scheduling order are required, not optional.
- **Shared mutable state** can produce surprising behavior under tasks. The
  reference must state the model directly instead of implying thread safety.
- **FFI v2** can compromise process safety. Ownership annotations, ABI checks,
  and platform tests are release blockers.
- **Cache artifacts** introduce a new supply-chain surface; versioning,
  invalidation, and trust must be specified before enabling by default.

## Completion criteria

A 1.5 change is complete only when its behavior is specified, tested against the
recorded baseline or semantic suite, documented in the versioned and master
references, covered by migration guidance when compatibility is affected, and
validated on every supported platform.

See the [1.4 roadmap](1.4.md) for the baseline and the
[long-term feature backlog](features.md) for candidates beyond 1.5.
